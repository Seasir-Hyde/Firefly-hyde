### 踩坑记录（重要）

1. **Aemeath 的 FriendsMagicPortal.astro 引用了不存在的 `../../scripts/friends-magic-portal.ts`** —— Firefly 原有版本照抄后组件一旦启用就 404，因为 `src/scripts/` 目录整个不存在。移植时补齐了脚本。

2. **延迟快照 JSON 格式两套互不兼容** —— Firefly 的是 59 站真实数据但缺 probeLocation/httpStatus/failureReason；Aemeath 的类型声明这些为必填。直接移植会导致显示 "undefined，探测于…" 和 "undefinedms"。解法：类型全部改为可选 + 工具函数兜底 + 探测脚本补写字段。

3. **TS1117 掩盖了 29 个其他类型错误** —— 原本 `pnpm type-check` 只有 5 个错误（全在 i18n 重复键），删掉重复键后暴露出 34 个 `--isolatedDeclarations` 错误（places-utils / icon-loader / content.config 等）。这些全是既有问题，与本次移植无关。**isolatedDeclarations 在遇到错误时会提前终止检查**，所以"修完错误错误变多"是正常现象，不代表引入了新问题。

4. **RSS 解析会把 HTML 404 页当 feed 解析** —— docs-firefly.cuteleaf.cn/rss.xml 返回 VitePress 404 HTML，被正则匹配出垃圾条目 + `1970-01-03` 异常时间戳。解法：`looksLikeFeedDocument()` 先校验 XML 特征（排除 `<!doctype html>`/`<html>`，要求含 `<rss>`/`<feed>`/`<channel>` 等），`parseDate()` 再排除 year < 2000 的误解析。

5. **纯 Node 环境跑不了 friends-feed** —— `content-utils.ts` 顶层 import `astro:content`，导致 `astro:content:` 协议不支持。解法：把 `getSortedPostsList` 改成惰性 `await import()`，只在处理本站 feed 时才加载，且 try/catch 兜底。

6. **`FRIENDS_FEED_WRITE_SNAPSHOT` 默认不写快照** —— Aemeath 全项目没有任何地方设置这个环境变量。需要显式 `pnpm refresh-friends-feed` 刷新。ESM import 会提升，脚本里必须用动态 import 保证环境变量先赋值。

7. **Aemeath 的推荐指南引用 `/posts/monthly-2026-09/`** —— Firefly 没有月刊文章，链接 404。已删除该链接并把"月刊第二期"相关文案改为本地语境。

8. **组件按钮类名不一致** —— Aemeath 用 `.friends-apply-button`，Firefly 用 `.friend-action-btn`。指南组件改用后者。

## seasir.top 延迟诊断与优化（2063ms → 目标 <500ms）

### 背景
友链延迟探测显示 seasir.top 为 slow / 2063ms / HTTP 200，用户希望进入绿色（fast <500ms）区间。
站点部署在 EdgeOne Pages（`npx edgeone pages deploy ./dist --name firefly-hyde`），域名托管在 Cloudflare。

### 关键教训：测量环境有代理
**本次诊断一开始全错。** 环境中存在 `https_proxy=http://127.0.0.1:11032`，curl 输出 `HTTP/1.1 200 Connection Established` 即代理隧道标志。
所有 curl/node fetch 测量必须加 `--noproxy '*'`（curl）或 `NO_PROXY` 环境变量，否则测到的是代理出口位置而非真实链路。
错误结论：一度判定"节点在新加坡是因为加速区域不含大陆"。

### 实际根因（三层，独立）

**1. DNS 记录类型错误（主因，收益最大）**
- `seasir.top` 权威 NS 确实是 Cloudflare（`ray/dana.ns.cloudflare.com`），但响应头无 `cf-ray`，说明是**灰云（仅 DNS）**，流量不过 CF 代理
- 根域用了 **A 记录直指 `43.174.246.36` / `43.174.247.36`**（腾讯 ACE 新加坡段），**没有 CNAME**（`resolveCname` → ENODATA）
- 这绕过了 EdgeOne 智能调度。标准链路是 CNAME → `pages.openedge.sched.txdl1.com`（sched=调度）→ 宁波节点 `115.238.171.185`
- 对比实测（`--resolve` 强制同一域名到不同节点）：
  - 新加坡 43.174.247.36 → TTFB 1500-3200ms
  - 宁波 115.238.171.185 → TTFB **64-83ms**（快 20-40 倍）
- 路由追踪佐证：第 10 跳 `202.97.43.74 → lax-b22-link.ip.twelve99.net`（TWCS 美国骨干），延迟 5ms→167ms
- 对照：cloud.tencent.com 直连 ttfb=0.15s，www.qq.com=0.11s
- 注意：`*.edgeone.app` → 43.168.176.154（新加坡，另一套调度集群）；本项目实际用 `*.edgeone.run` / `*.edgeone.site` → 宁波

**2. edgeone.json 未被部署（缓存从未命中）**
- `edgeone pages deploy ./dist` 只上传 `dist/`，仓库根目录的 `edgeone.json` 不在其中 → Pages 用控制台默认 `Cache-Control: public, must-revalidate, max-age=0`
- 实测 `EO-Cache-Status: MISS` 恒定，`Age` 有值但每次都回源验证
- 静态资源 `/_astro/*`、`/assets/*` 是 HIT（`immutable, max-age=31536000`），说明只有 HTML 规则失效
- 官方文档：edgeone.json 需在"项目根目录"，CLI 部署时即被上传目录
- 官方另有 `Pages-Cache-Control` 头专门控制边缘缓存（与给浏览器的 `Cache-Control` 分离）

**3. 探测脚本测的是冷缓存**
- 原 `measureFriend` 追加随机 query `_friend_ping=<ts>-<rand>` + `cache: "no-store"` → CDN 每次必然回源
- 测出的是"源站裸响应"而非"访客真实体验"，对已开边缘缓存的站点高估 1~4 秒
- 改用干净 URL + 真实浏览器 UA 后：2063ms → 1466ms（仍 slow，因为缓存规则本身没生效）

### 已知约束
- Cloudflare DNS 托管的**根域名不支持 CNAME 接入**（CNAME 与其它记录互斥），需改用 www 子域名
- 橙云（Proxied）会导致双重 CDN 减速 + Error 520/522 + EdgeOne 证书签发失败（CA 到不了 EdgeOne 边缘）
- 无 CAA 记录，证书签发无阻碍
- EdgeOne Pages 免费版加速区域选定后不可反向切换

### 已改代码
